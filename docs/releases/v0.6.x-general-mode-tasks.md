### 1.1 分類漂移防線

任務表最容易腐爛的地方是「某天它其實做得到了，文件卻還寫著做不到」，反過來也一樣。
所以每個任務在 spec 裡**事先宣告**分類（`TASK_MANIFEST`），`record()` 會拿實跑結果去對：

- 宣告 `correctly-blocked` 的任務，spec 必須同時提出三份證據才算數——動作前後的**後端狀態
  JSON 完全相同**、畫面上真的有一句誠實文案、**動作的目標**沒有長出綠勾。少一項就直接紅。
  第三項的範圍刻意收斂到「被按下的那張卡片／那一格設定」，不是整頁：頁面上同時存在別的、
  **真實**的成功狀態（手機已同步、另一個角色「使用中」），把它們一起掃進來會讓這個檢查
  變成噪音，然後遲早被人放寬掉。
- 宣告與實跑不一致（做得到了／退化成拒絕）也直接紅，訊息會指名是哪個任務漂移了。
- 每輪產出 `apps/interaction-desktop/test-results/general-mode-task-outcomes.json`：
  任務 → 宣告分類 → 實跑分類 → 證據等級 → 限制 → 完整量測。沒跑到的任務誠實記成
  `not-run`（不是通過，也不是失敗）。

## 2. 任務量測

### 2.1 本輪實跑（自動化，`taskMetrics.ts` 的計數規則）

計數規則（`src/test/general-mode-metrics.test.tsx` 是它的合約）：

- **主要決策**＝使用者必須自己選的事（同時算一次點擊）。
- **安全步驟**＝不可省略的確認（算點擊、**不**算決策——省掉安全步驟不是進步）。
- **回頭**＝導覽回到造訪過的頁面。
- **求助**＝任務中「必須另外去找說明才做得下去」的次數。刻意**不**自動計點擊：受測者的
  口頭求助沒有點擊，自動化裡真的按了什麼就自己再記一次點擊——同一份定義才能同時用在
  §2.1 的自動化與 §4 的真人腳本上。
- **失敗後恢復**＝任務中是否至少一次「出現失敗／被拒絕之後，靠畫面上的指示回到可繼續的
  狀態」。是布林：恢復過就是恢復過，次數多不代表更好。
- **耗時**＝量測開始到結束的實際牆鐘時間。這是**機器**的耗時，不是人的：它只說明
  「畫面有沒有卡住」，**不得**被讀成「一般人做完這件事要幾秒」。

目標「一般任務 3–5 個主要決策」以**上限**解讀：每一列都 ≤ 5，spec 內以
`withinDecisionTarget()` 斷言（超過就紅）。幾個容易被誤讀的欄位：

- 決策數 0 的四列是誠實的事實而不是漏測：「手機與桌面互動」「暫時離線後恢復」
  「等待離線逾時」的動作發生在手機端，桌面端**不需要**任何決策就會自己更新（SSE 推送）；
  「調整陪伴程度」在瀏覽器模式**做不到**（Tauri-only），0 代表「這裡連按都沒得按」，
  不代表「一步就完成」。
- **求助全部是 0，只代表這一輪的自動化腳本沒有走進任何說明**——腳本知道路，不會迷路。
  這個欄位真正的用途在 §4 的真人腳本；把它讀成「介面好懂到沒人需要說明」是誤讀。
- **失敗後恢復全部是「否」**：這一輪沒有任何任務在中途踩到失敗。它**不是**「系統不會失敗」
  的證據——這個欄位存在，是為了在真的有失敗時記得下來，而不是讓失敗悄悄從報告裡消失。
- 「等待離線逾時」的 46.3 秒是**真的等**：presence 逾時是 45 秒，沒有可調的環境變數。
  其餘任務的秒數都在個位數，因為本機 daemon 的回應是毫秒級——這只證明畫面沒有卡住。

## 4. 非開發者測試腳本（**尚未有受測者、尚未執行**）

> 狀態：**未執行**（`not-run`）。以下五份腳本是給之後真的找人來測時用的；本輪**沒有**招募
> 任何受測者，也**沒有**任何觀察紀錄。任何人不得把 §2／§3／§3.5 的自動化數字當成這五份
> 腳本的結果。

共同規則：受測者不看文件、不問旁邊的人；主持人只記錄，不提示。每一步記下
**時間**、**是否卡住**、**卡在哪一句話**。出現任何安全確認（二段確認、套用前確認）時，
記錄受測者是否讀了那句話再按。

主持人用**與 §2.1 同一份定義**記這幾個欄位（`taskMetrics.ts`），這樣真人結果才有辦法與
自動化並排看：

| 欄位 | 真人腳本怎麼記 |
| --- | --- |
| 主要決策 | 受測者自己要選的事（同時算一次點擊） |
| 安全步驟 | 不可省略的確認；**不**算決策 |
| 點擊 | 找路、展開、切分頁這類純操作 |
| 回頭 | 導覽回到先前造訪過的頁面 |
| 求助 | **開口問主持人、或去翻說明的次數**（口頭求助沒有點擊，所以不另計點擊） |
| 失敗後恢復 | 是否至少一次「碰到失敗／被拒絕之後，靠畫面上的指示自己回到可繼續的狀態」 |
| 耗時 | 從「開始這個任務」到「受測者說做完了」的牆鐘時間（**與 §2.1 的機器耗時不可比較**） |

### P1「第一次打開」（沒用過這個程式的人）

1. 打開控制中心，照畫面走完首次設定。
2. 走到最後一步時，先講一句「你覺得按下去會發生什麼事」再按。
3. 回到「現在」這一頁，用自己的話說出畫面上三件事分別在講什麼。
4. 找到「角色現在怎麼樣」，說出它現在是什麼狀態。
5. 找到緊急停止在哪裡（**不要按**）。

- 成功判準：不需要提示就走完三步＋套用；能說出「現在」三件事各是什麼；十秒內指出緊急停止。
- 要記錄：在哪一步停下來最久；套用前確認那一段有沒有被讀；有沒有把「首次成功體驗」當成必要步驟。

### P2「把手機接上來」（有 iPhone、沒接過的人）

1. 從角色頁找出「手機還沒接上」這件事。
2. 用畫面上的下一步按鈕，走到可以開始配對的地方。
3. 開始配對，把配對碼唸出來。
4. （主持人操作測試手機完成配對）回到角色頁，說出現在同步狀態是什麼。
5. 說出「已連接」和「已同步」在這個畫面上是不是同一件事。

- 成功判準：不需要自己去翻「連接與權限」的第二層分頁；能講出目前狀態不是「全部完成」。
- 要記錄：有沒有把「iPhone 已連接，能力核對中」誤讀成成功；配對碼有沒有找不到。

### P3「太吵了，讓它安靜」（覺得被打擾的人）

1. 從角色頁找到跟「安靜」有關的地方。
2. 說出畫面上列的幾種「安靜」分別管的是什麼。
3. 設定一段安靜時段（起訖自訂）。
4. 說出設定之後**還會不會**收到安全提示與感測提示。
5. 把安靜時段關掉。

- 成功判準：找得到、設得成、關得掉；能說出「安全提示與感測提示不受安靜設定影響」。
- 要記錄：有沒有以為「安靜」是一個開關；有沒有去找勿擾卻找到主動對話。

### P4「我要它停下來」（安全情境）

1. 交代一件工作（隨便一句話）。
2. 在它進行中把它停掉。
3. 說出畫面現在說這件工作是什麼狀態。
4. 按下緊急停止，走完確認。
5. 說出現在要怎麼把系統恢復。
6. 走完解除流程。

- 成功判準：不需要提示就找得到中斷；能說出「已取消」與「對方說已完成」不一樣；解除時願意走完兩段確認。
- 要記錄：二段確認有沒有被當成多餘；解除流程有沒有人想找「一鍵恢復」。

### P5「手機上的畫面跟電腦不一樣？」（同步語意）

1. （已配對狀態）看角色頁的「同步」卡，說出它現在在講什麼。
2. （主持人讓測試手機離線）說出畫面現在說什麼、你會不會擔心。
3. 等一分鐘，再說一次畫面說什麼。
4. （主持人讓手機接回來）說出現在是不是恢復了。
5. 主動移除這台手機，說出移除之後畫面說什麼。
6. 說出「要再用手機」需要做什麼。

- 成功判準：能分辨「正在重新連線」「暫時離線」「目前只在這台電腦使用」三句話的差別；
  移除之後不會覺得「壞掉了」。
- 要記錄：有沒有人在「正在重新連線」時就去重新配對；移除後的終態句會不會被當成錯誤。
