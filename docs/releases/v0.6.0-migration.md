## 1. 新增 HTTP 路由（human token）

| 路由 | 用途 | 來源 |
|---|---|---|
| `GET /v1/character-session` | 權威 snapshot（`state{kind:"snapshot"}` envelope） | `crates/interaction-api/src/routes.rs::character_session_snapshot`(:1846) |
| `POST /v1/character-session/resume` | `{lastRevision,lastSequence,epoch}` → patches 或 snapshot | `routes.rs::character_session_resume`(:1876) |
| `POST /v1/character-session/events` | 可信 host surface（桌面）送語意事件 | `routes.rs::character_session_event`(:1902) |
| `GET /v1/character-session/diagnostics` | 不含 token／路徑／原始 payload 的計數與成員列表 | `routes.rs::character_session_diagnostics`(:1856) |

四條路由都受 `INTERACT_AI_CHARACTER_SESSION` feature flag 管制（§5）；`agent` token／agent session
capability token／character adapter token 一律拒絕（human-only，`docs/aip/transport-bindings.md` §2）。
拒絕機制與狀態碼見 §10.1。

## 2. 新增事件（SSE）

`character.session.state`（`GET /v1/events`，human token）：payload 是完整 AIP envelope
（`state{kind:"patch"｜"snapshot"}`），每次廣播都送一次；`capability`／`command`／`result` 送給桌面
可信 host surface 時也走這個事件型別。與既有 `character.*` 事件同界線：agent token／adapter token
一律看不到。事件型別的 Rust 定義：`EventType::CharacterSessionState`
（`crates/interaction-core/src/event.rs:112`，wire 字串 `"character.session.state"` 在 `:164`）。
SSE 分派：`crates/interaction-api/src/sse.rs:51`／`:177`。詳見 `docs/aip/transport-bindings.md` §3。

### 8.3 SSE `character.session.state` 的前端消費

`apps/interaction-desktop/src/components/CharacterSyncCard.tsx:54`：
`const SESSION_STATE_EVENT = "character.session.state"`；事件比對在 `:291`
（`if (event.eventType !== SESSION_STATE_EVENT) continue;`）。消費策略（見檔案頂端 :1-29 的設計註記）：

- `GET /v1/character-session` 會消耗一個 session sequence，因此**權威狀態改由 SSE payload
  直接更新本地副本**：`snapshot` 整份取代，`patch` 用 RFC 7396 merge patch（`../aip/envelope.ts`
  的 `applyMergePatch`）套上去；只有首次載入、`baseRevision`／`epoch` 接不上、或使用者按「重新
  檢查」才會再 GET 一次。
- 桌面端刻意不做接收端 hash 核對（JS number 留不住 Rust `0.0` 這類字面值，canonical JSON 逐位元
  組比對一定會產生假警報）；不一致時改用 revision 單調遞增與 `baseRevision` 相符來判斷。
- 裝置清單／來源清單／診斷不消耗 sequence，但節流成最小間隔 2 秒（`SYNC_SLOW_REFRESH_MIN_MS`）的
  trailing 重取。

掛載點：`apps/interaction-desktop/src/pages/CompanionPage.tsx:17`（import）／`:309`
（`<CharacterSyncCard refreshKey={refreshKey} advanced={advanced} sessionEvents={events} />`）；
Runtime SSE 事件流的來源在 `App.tsx`。

## 10. Breaking 變更

### 10.1 對外部呼叫者：沒有 breaking

- **舊 iPhone App（不送 `capability` 的版本）**：完全不受影響。iPhone 線協定 v1 的既有訊息全部
  保留，`aip` frame 是全新增訊息型別，`character.present` 動器與 `iphone.touch` observation 路徑
  不變。沒送過 `capability` 的舊 App **永遠不會**收到任何 `aip` frame——回歸測試見 §9.8。
- **對 HTTP 既有路由**：沒有 breaking。§1 的四條路由全部是新增路徑（`/v1/character-session*`），
  沒有修改任何既有路由的請求／回應形狀。非 human token（agent／agent session capability／
  character adapter）打這四條新路由一律 403：GET 由 `agent_request_allowed`
  （`crates/interaction-api/src/lib.rs:478`）在 `!path.starts_with("/v1/character")` 這個既有排除
  規則下自動涵蓋（`:493` 註記「`/v1/character-session*` 也在這個前綴內」）；POST（`resume`／
  `events`）落在同一函式尾端的白名單比對（:520-524，`path == ... \|\| ...` 鏈，是函式的隱式回傳
  值），character-session 路徑不在白名單內，回傳 `false`；`adapter_request_allowed`（:415-418）只
  白名單 `/v1/character/receipts`／`/v1/character/events` 兩條 POST，character-session 路徑同樣不
  在其中；`session_request_allowed`（:420-458，agent session capability token）也沒有
  character-session 的分支。三種非 human token
  一律在 middleware（`lib.rs:386` agent、`:390` session capability、`:394` adapter）被擋為
  `forbidden_scope`／`forbidden_adapter_scope`（403）。
  Flag 關閉時（`INTERACT_AI_CHARACTER_SESSION=0`）四條路由在 human token 通過驗證*之後*才在 handler
  內回 503（`routes.rs::require_character_session`，見 §5），即 403（身分）先於 503（功能開關）判定。
- **對 CLI 既有子指令**：沒有 breaking。`interact-ai character session ...` 是全新子命令樹，沒有
  修改任何既有子命令的參數或輸出格式。

## 11. 升級／回退

- **Feature flag 回退**：`INTERACT_AI_CHARACTER_SESSION=0` 使行為回退到 v0.5.1（見 §5）。這是
  唯一官方支援的「整批關掉」開關；回退不需要刪除任何檔案或改資料格式。
- **`state/character-session.json` 可刪除重建**：
  - 檔案不存在（例如手動刪除）：`CharacterSessionHost::open`
    （`crates/interaction-runtime/src/character_session.rs:189`）視為全新 session，
    `epoch` 從 `1` 起算（`character_session.rs:209`，`CharacterSession::new(config, 1, now)`）。
  - 檔案存在但讀不到／解析失敗：`store.quarantine()`（`character_session.rs:97-107`）先嘗試從壞
    檔案內容「挽救」原本的 epoch（`salvaged_epoch`），挽救不到就當 `0`，一律 `+1`；壞檔案改名為
    `character-session.json.corrupt` 隔離（不覆寫、不吞掉，供事後排查），新 session 以挽救後的
    `epoch` 起算。診斷／同步卡只顯示固定文字（不含錯誤細節、路徑），對應 §8.4 的 `store-reset` 態。
  - 兩種情況都會在下次啟動立刻落一份新快照（`character_session.rs:219-220`），重啟後续接得到
    revision／epoch，不會默默從頭開始又不留痕跡。
- **`state/character-session.epoch` 也可刪除**（`crates/interaction-runtime/src/character_session.rs::SESSION_EPOCH_FILE`，
  權限 `0600`）：這個檔案只有一個十進位整數（本機用過的最大 `sessionEpoch`），沒有任何個人資料或
  裝置識別碼。它的存在是為了讓「快照被隔離或整個被清空」之後的新 epoch 仍然大於成員記得的值。
  **可以與 `character-session.json` 一起刪除**；兩個都刪掉之後，epoch 從**牆鐘秒數**（unix 秒）
  重新起跳（`next_epoch()` 的 `fresh_epoch_seed()`），那個值保證大於任何以 1 起算的遞增 epoch，
  所以舊裝置重連時仍會正確拿到 `session-reset`，不會出現「epoch 撞號、兩邊都以為已同步」。
  只刪 `.json` 而留著 `.epoch` 也是安全的（epoch 會從記住的值 +1）。
- **`SemanticState` 的 `members[]` 在 v0.6.0 新增 `unsupportedIntents`（只加欄位）**：
  這個欄位進了 canonical state，所以**這個欄位出現之前寫下的快照會被 `restore` 判成
  `HashMismatch`**（只有本實作寫得出來的 canonical state 才能成為權威狀態），host 會把它隔離成
  `.corrupt`、開一個新 session（epoch 往前跳），診斷／同步卡顯示 `store-reset` 的固定文字
  （「角色同步紀錄曾損毀，已重新開始」）。v0.6.0 尚未發布，因此這只影響**開發期**留下的快照；
  對使用者的實際效果是「已連接的裝置重新同步一次，角色本身不受影響」。
- **Epoch 語意**：`epoch` 是「session 有沒有被重建過」的粗粒度標記。`resume`（`crates/interaction-session/src/session.rs:577`）內：`epoch` 與呼叫端記得的不同（:586-588）→ 一律回傳
  `Resume::EpochMismatch`，附帶 `reason: "session-reset"` 的完整 snapshot（不嘗試套 patch，即使
  revision 數字看起來接得上）；`epoch` 相同才進入「用 revision／sequence 判斷回 patches 還是
  snapshot」的一般路徑（:590 起）。因此：只要用戶端誠實記住自己上次看到的 `epoch`，刪除／損毀
  `character-session.json` 這類「host 端狀態重建」永遠會被用戶端正確偵測為需要整份重新對齊，
  不會有「epoch 變了但用戶端誤套舊 patch」的錯誤路徑。iOS 端有對應驗證：
  `SessionClientTests.swift::testSessionResetWithANewerEpochIsAcceptedEvenThoughTheRevisionGoesBackwards`
  （:185）。
