> 接一台新形狀的裝置／在權威狀態上加一個欄位／停用再啟用一個 adapter／移除一個套件，分別要
> 碰到哪些模組，以及核心裡有沒有為了它而長出角色或裝置的特判。

> **演練 1 與演練 3 的程式碼做在本機的演練分支 `wt/drills` 上，那個分支不合併、也沒有推到
> origin**。第三個內建角色 `ref-dot`、`SemanticState.ambient`、`crates/interaction-session/tests/optional_state_field.rs`

> 去 repo 裡找它們會找不到，那是預期的。演練 2／4／5 的產物（`examples/adapters/event-source-button.yaml`、
> `scripts/drills/*.sh`、`declarative_session_loop.rs` 的那支測試）與 §7 的缺口清單則已經在本分支上。
> 文件裡一律用檔案路徑引用，不引用 commit id。

## 2. 接入受限裝置：只回報事件的按鈕盒（`syncProfile: event-source`）

## 4. 停用及重新啟用 Adapter（對真的 daemon）

**目標**：把 `docs/aip/device-profile.md` §6.1 與 `docs/aip/adapter-development.md` §5 描述的
生命週期真的走一次：停用 → 重新啟用（觀察 `disconnected → rebinding → available`）→ 撤銷之後
不得復活。**不改任何程式碼**。

**實際命令**

```bash
$ bash scripts/drills/provider-disable-reenable.sh 8873
```

腳本自己做完：起 pty 模擬器 → 把 `examples/adapters/event-source-button.yaml` 換掉埠寫進
隔離 home 的 `config/adapters/` → 用 `INTERACT_AI_HOME=$(mktemp -d)`、自選埠、
`INTERACT_AI_MOBILE_ADVERTISE=0` 起真 daemon → 逐步用 CLI 操作並印出每一步。

**`git diff --stat`**

```
 scripts/drills/provider-disable-reenable.sh | 108 ++++++++++++++++++++++++
 1 file changed, 108 insertions(+)
```

只有腳本；**產品程式碼零變更**。

**每一步的實跑輸出**

| 步驟 | 觀測 |
|---|---|
| 0）綁定 | `state=available` |
| 1）`providers transition … --state disabled` | `state=disabled`；稽核 `provider.capabilities-disabled{reason:"disabled", receptors:["button-box.button"]}`＋`provider.transitioned{closedLinks:["serial /dev/ttys003@115200"], sensorStop:{reason:"provider-stopped", released:{declarationRetracted:true, leftSession:["button-box-01"]}}}` |
| 2）`--state available` | **transition 的回應本身**是 `state=disconnected`，detail 多一句「正在重新連上這台裝置，它的能力還沒有回來；連上之後才會顯示為可用。」——ProviderState 沒有先於實際連線 |
| 2b）約 1 秒後 | `state=available` |
| 3）稽核 | `provider.rebinding{generation:1, previousLinks:[]}` → `provider.rebound{generation:1, handshake:"ready", drained:true, keptDisabledReceptors:[], staleChannels:[]}` |
| 4）`providers revoke` | `state=revoked`；稽核 `provider.revoked{closedLinks:["serial …"], sensorStop:{reason:"provider-stopped"}}`＋`provider.capabilities-disabled{reason:"revoked"}` |
| 5）撤銷後再 `--state available` | API 拒絕：`validation_failed: illegal lifecycle transition Revoked → Available (pairing, install, enable and consent are separate steps)`；`state` 仍是 `revoked` |

**核心有沒有出現特判**：沒有。整條路徑走的是 `declarative_lifecycle.rs` 的世代化狀態機，
稽核 detail 裡沒有任何裝置種類的分支——`closedLinks` 只是把傳輸自己回報的字串（`serial …`）
原樣列出來。

**一個誠實的邊界**：`DeclarativeLifecycle::{Bound, Rebinding, Unbound}` 本身**沒有**經由 HTTP
或 CLI 直接曝光。人能看到的是 `ProviderState`（`available`／`disabled`／`disconnected`／
`revoked`）＋`detail` 的人話＋稽核事件。要斷言 `Unbound{Disabled}` 只能靠 Rust 測試
（`declarative_session_loop.rs`）。這不是缺陷，但寫文件時不要把它說成「CLI 讀得到 Unbound」。

**測試與數字**：這一項沒有新增自動化測試；腳本是**可重跑的演練**，實跑三次（埠 8872／8873／8874）
結果一致。既有的回歸測試仍然是
`declarative_session_loop::{reenable_rebinds_without_restart, rebind_generation_rejects_late_callbacks,
revoke_during_rebind_does_not_resurrect, rebind_timeout_is_bounded_and_honest}`（本輪整檔 26/26 綠）。

**耗時**：約 30 分鐘（估計；含第一次 `set -u` 踩到全形冒號被當成變數名的坑）。

**結論**：這條路徑的可觀測面**夠用但分散**（state ＋ detail ＋ 稽核三處）。腳本化之後它從
「要讀四份文件才知道怎麼看」變成一行命令。

   （`apps/interaction-desktop/src-tauri/src/character_store.rs` 的版型）。
2. 使用者資料指向它：後端 `prefs.customNames = {"party-lamp":"我的派對燈"}`；
   `state/desktop.json` 帶 `companionPack`／`companionName`／`storyProgress`／
   `companionPreferences`／`companionInteractionMemory`；另註冊一個外部 adapter token 產生稽核。
3. 移除套件：`rm -rf <home>/state/characters/party-lamp`——`character_store::remove` 做的
   **就是**對那個資料夾 `remove_dir_all`（外加「內建角色不可移除」與路徑逃逸檢查）。
4. 重啟 daemon，逐項核對：

| 項目 | 移除＋重啟前 | 移除＋重啟後 |
|---|---|---|
| `state/desktop.json` | `sha256=b3764b38c5897f35`，357 bytes | **完全相同** |
| `prefs.customNames` | `{"party-lamp":"我的派對燈"}` | 相同 |
| 稽核筆數 | 1 | 1 |
| `character-session.json` | `epoch=1 revision=1` | `epoch=1 revision=33` |
| 隔離／遷移檔 | — | 沒有 `.corrupt`、沒有 `.pre-format-*` |
| `character status` | — | `{"activeCharacter": null, "instances": 0, "version": "1.0"}` |

`epoch` 不變＝快照是**還原**不是重建（重建會換 epoch，成員全掉）；`revision` 前進是重啟後
presence tick 的正常結果。daemon 側誠實回 `activeCharacter: null`，沒有假裝角色還在。

**核心有沒有出現特判**：沒有——而且這裡的「沒有」是**結構性的**：使用者資料根本不住在套件
資料夾裡（prefs 在後端、`desktop.json` 在 Tauri host、session 快照在 runtime、稽核在 SQLite），
所以「移除套件保留資料」不是靠一段小心翼翼的程式碼，是靠一開始就沒有把它們放在一起。

**誠實邊界**：Tauri 桌面沒有在這裡跑，所以 `state/desktop.json` 是照
`apps/interaction-desktop/src/desktop.ts` 的 `DesktopPrefs` 形狀**手寫**的；角色頁的
「找不到／壞掉／不在白名單 → 退回文字角色＋原因」由既有桌面單元測試涵蓋，不是這支腳本驗的。

**測試與數字**

| 測試 | 結果 |
|---|---|
| `companion-imported-characters.test.ts` ＋ `characterPage.test.tsx` | **48 passed / 0 failed** |
| 腳本實跑 | 埠 8876／8877／8878 三次，結果一致 |

**耗時**：約 25 分鐘（估計）。

**結論**：這一項是五個演練裡最乾淨的。唯一的意外是「移除」這個入口住在 Tauri host
（`character_store::remove`），daemon 完全不知道有這件事——所以 CLI 上沒有
「移除已匯入角色」的對應指令。
